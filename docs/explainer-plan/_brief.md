## 每門課要產出的內容

### A. 教材確認（現有文字內容有沒有問題）
逐章檢查，只列出真正的問題，每條附章節 id 與原文片段：
- **會教錯**：技術上錯誤、過時、或只在特定條件成立卻說成通則的說法。能在本機實測的請實測並附結果（只准在系統暫存資料夾操作，不准連網、不准安裝軟體）；無法實測的標「未驗證，依據：…」。
- **順序問題**：名詞或概念在解釋之前就被使用；後面的章節用到前面沒教過的東西。
- **前後矛盾**：同一門課或跨課之間，同一件事說法不一致；例子的名稱、位址、版本前後不同。
- **看不出重點**：一章塞了兩個以上不相干的主題。
沒有問題的章節寫「未發現問題」即可，不要湊數。

### B. 互動講解的規劃
1. **這門課的共用例子**：一個具體情境，加上名稱與代號表（主機名、位址、帳號、版本等，全課唯一）。同一條路線的各門課盡量沿用同一家虛構公司與同一組名稱。
2. **畫面的隱喻**：這門課裡每種形狀代表什麼。
3. **課序是否要調整**，以及是否有章節應該拆開或合併（一課只回答一個問題）。現有的章節 id 不可改名或刪除，只能調整順序或新增。
4. **逐章規劃**。每一章先判斷：
   - 「做互動講解」：這一章在講機制或流程，看得見東西怎麼動會比文字好懂。
   - 「維持文字」：清單型、操作步驟型、純環境安裝。寫一句原因即可，不必往下規劃。
   要做的章節，寫出：
   - 這一課要回答的問題（用讀者會問的話）
   - 「看完你能…」一句
   - 3～4 張卡，每張：**標題（一句結論）**、舞台要呈現的「操作前後差異」是什麼、用哪種場景（現有五種之一，或「需要新場景：〈名稱〉」）、控制型式、銜接句
   - 重點回顧三點
   - 隨堂檢測的題目方向與正解（選項要是新人真的會有的誤解）
   - 要移到「動手做」的內容
   - **事實性陳述**：這一課會講到的、可以驗證真假的說法，逐條列出並標「已實測／依文件／未驗證」
   不需要寫出每個控制按下後的確切說明列文字，那是實作階段的事；但卡片標題與舞台的差異要具體到實作者不必猜你想呈現什麼。
5. **需要的新場景**：彙整這門課需要、但現有五種沒有的場景。每種寫：名稱、畫面上有什麼、view 需要哪些欄位（參考 types.ts 的寫法）、哪幾章會用到、是否值得用 three.js（依 stage-catalog.md 的三個條件判斷，並說明沒有 WebGL 時的平面版長什麼樣）。盡量讓一種場景被多章共用，不要每章發明一種。
6. **優先順序**：這門課裡哪幾章最值得先做，為什麼。

## 規則
- 嚴格遵守 interactive-lesson 的五條架構原則與 design-rules.md。特別注意：一種形狀只代表一種東西；複製與移動要分清楚；隱含狀態（「目前在哪」之類）從第一張卡就要畫出來；後面的課只用前面教過的名詞。
- 不要為了互動而互動。清單型的章節就判「維持文字」。
- 不確定的技術事實不要寫成肯定句，標「未驗證」。
- 只寫一個檔案：你被指派的輸出檔。不要修改其他任何檔案，不要執行 git 指令。
- 輸出用繁體中文，文件開頭先放一段摘要：共幾章、幾章建議做互動講解、發現幾個會教錯的問題、需要幾種新場景。
