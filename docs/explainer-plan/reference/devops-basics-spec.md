# 互動講解頁設計規格與腳本 v2（devops-basics 課程）

v2 依對抗式審查的裁決（rulings-r2.md）改寫，取代 spec.md。
讀者：完全沒碰過 Git 與 CI/CD 的新人。平台：純靜態 React 網站，繁體中文（台灣用語），技術名詞保留英文。

---

## 第一部分：頁面架構（所有課共用）

### 1. 一課一頁，一課只回答一個問題
- 課程頁只列出這門課有哪幾課：每課一張卡，顯示「第幾課／這一課要回答的問題／預估分鐘數」，點進去才是內容。
- 每課有自己的頁面與網址（`#/courses/<課程 id>/<課 id>`），上方兩個分頁：**講解**（預設）與**動手做**（網址加 `/practice`）。切換分頁不保留舞台狀態。
- 講解分頁只放第二部分的腳本；指令練習、手把手解答、常見問題、速查、延伸說明一律放「動手做」分頁。

### 2. 講解分頁的版面
- 單欄、最大寬度 720px、置中，卡片之間留白 32px 以上。
- 頁首：返回課程頁的連結「‹ 課程名稱」＋「第 N 課／共 3 課」；這一課的問題（大標）；一句「看完你能…」。
- 進度列固定在畫面頂端（捲動時不消失）：顯示各卡編號與「回顧」「檢測」，目前所在的那一格以強調色標示，可點擊跳轉。
- 內容順序：3～4 張概念卡 → 重點回顧 → 隨堂檢測 → 兩顆按鈕。主要按鈕是「下一課」（最後一課改為「回到課程頁」），次要按鈕是「去動手做」（等同切到動手做分頁）。

### 3. 一張概念卡的固定結構
1. 編號。
2. **標題是一句結論**，只講一件事。
3. 說明文字：最多 60 個中文字。寫「這件事是什麼」。第一次出現的名詞，當下用半句話解釋。
4. **一個舞台，三層**：
   - 控制列：最多 3 個主要控制。按鈕有先後順序時，後面的按鈕在前一顆按過之前呈停用狀態。
   - 畫面：一個場景（同一個場景裡可以有多個物件，例如三個托盤；但不放第二個獨立面板，也不放多欄表格）。
   - 說明列：最多兩句短句，隨操作改變。第一句說「現在看到的是什麼」。
   - 舞台右上角固定有一個小的「↺ 重來」文字連結，回到初始狀態；它不算在 3 個控制內。
5. 最後一行是銜接句，帶到下一張卡（最後一張卡沒有）。
- 每個舞台的初始狀態、每個控制按下後的畫面與說明列文字，都寫在第二部分。沒寫到的操作一律「沒有效果」（按鈕停用）。

### 4. 視覺規則（講解與動手做分頁內）
- 紙色底，卡片白底、1px 淡框、無陰影、不傾斜。貼紙風格不進到這兩個分頁。
- 全頁只有一個強調色（蜂蜜黃），用在：目前選取的選項、主要按鈕、進度列目前位置、舞台中「剛剛發生變化的那個物件」。選取狀態除了底色還要有 2px 深色框，不只靠顏色。
- 綠色與紅色只表示「通過／失敗」，而且一律搭配符號（✓、✕）與文字，不只靠顏色。未執行的關卡用灰色加「未執行」文字。
- 內文深墨色；次要文字對比至少 4.5:1；內文不小於 15px。
- 動畫只呈現狀態改變。使用者開啟「減少動態效果」時，所有變化直接跳到結果，不播動畫。

### 5. 窄螢幕、鍵盤與輔助技術
- 寬度小於 640px：橫向排列的關卡改為直向清單；控制列的按鈕可以換行（仍不超過 3 個）；Git 歷史圖可橫向捲動。
- 3D 場景在寬度小於 640px、或瀏覽器無法使用 WebGL 時，改用同一內容的平面版（三個並排或直向堆疊的格子，方塊代表 commit）。互動與說明列文字完全相同。
- 所有控制都是可用鍵盤操作的按鈕，有可見的焦點框。
- 說明列的變化要能被螢幕閱讀器讀到。3D 與圖形畫面需有一句文字描述目前狀態（與說明列相同即可）。

### 6. 整門課共用同一個例子、同一段歷史
情境：你在公司的「請假系統」專案，要把首頁按鈕上的錯字「送出申情」改成「送出申請」。目前線上是 v1.3.0，這次要上 v1.4.0。

整門課只有這一段歷史，字母永遠代表同一次存檔：

| 代號 | 是誰的、做了什麼 | 在哪條線上 |
|---|---|---|
| A | 專案最初的存檔 | main |
| B | v1.3.0 上線時的存檔（按鈕文字是錯字「送出申情」） | main |
| C | **你**修錯字：「送出申請」 | feature/fix-typo |
| D | **同事**在別的頁面加了說明文字（沒有碰那顆按鈕） | main |
| M | 把 C 併進 main 的合併點 | main |

- `feature/fix-typo` 永遠是**你的**分支。
- 第 1 課卡 4 的衝突是「假設情況」：假設同事的 D 也改了同一顆按鈕。卡片上要明寫「假設」。

## 第二部分：三課的腳本

課序：先學會看分支（第 1 課），再學本機與遠端（第 2 課），最後看整條上線流程（第 3 課）。後面的課只用前面教過的名詞。

### 第 1 課　branch 到底是什麼？為什麼不直接改 main？（約 5 分鐘）
看完你能：看懂一張 Git 歷史圖，並說出開分支、合併、衝突各是什麼。

**卡 1　commit 是一次存檔，一顆接一顆串成歷史**
- 說明：Git 把每一次存檔（commit）串成一條線。`main` 是一張標籤，標出這條線目前的最新位置。
- 舞台
  - 初始：一條線上只有 A，`main` 標籤貼在 A，A 上有「你在這裡」的記號。說明列：「現在只有一次存檔 A。」
  - 控制：一顆「commit」。按一次：出現 B，`main` 與「你在這裡」一起移到 B，按鈕停用。說明列：「多了一次存檔 B。main 跟著往前移。」
- 銜接句：如果每個人都直接在 main 上存檔，改到一半的東西會互相影響。

**卡 2　開分支是多貼一張標籤，再站到它上面**
- 說明：分支（branch）也是一張標籤。`git switch -c` 會貼上新標籤，並把「你在這裡」移過去；之後的存檔只會推動你站著的那張。
- 舞台
  - 初始：A—B，`main` 在 B，「你在這裡」在 `main`。說明列：「你現在站在 main 上。」
  - 控制 1「git switch -c feature/fix-typo」：B 上多一張 `feature/fix-typo` 標籤，「你在這裡」移到新標籤。說明列：「多了一張標籤，沒有複製任何檔案。你現在站在 feature/fix-typo 上。」
  - 控制 2「commit 修錯字」（控制 1 之後才可按）：從 B 岔出 C，`feature/fix-typo` 與「你在這裡」移到 C，`main` 留在 B。說明列：「新的存檔只推動你站著的那張標籤。main 沒有動。」
- 銜接句：改好了，怎麼讓 C 回到 main？

**卡 3　merge 用一個新的 commit 把分岔的兩條線接起來**
- 說明：你改錯字的期間，同事的修改也進了 main，兩條線分岔了。合併（merge）會產生一個新的 commit，同時接上兩邊。
- 舞台
  - 初始：A—B，B 岔出 C（`feature/fix-typo`），`main` 在 B。說明列：「你的 C 在分支上，main 還在 B。」
  - 控制 1「同事的修改進了 main」：main 這條線上出現 D，`main` 移到 D。說明列：「main 多了同事的 D。現在兩條線分岔了。」
  - 控制 2「merge」（控制 1 之後才可按）：出現 M，同時連到 D 與 C，`main` 移到 M。說明列：「M 同時接上 D 和 C。在公司裡，這一步通常是在 GitLab 上按下合併按鈕完成的。」
- 銜接句：這次很順利，因為同事沒有碰那顆按鈕。假設他也改了呢？

**卡 4　兩邊改到同一行，Git 會停下來讓你決定**
- 說明：這叫衝突。**假設**同事的 D 把同一顆按鈕改成「確認送出申情」。你把 main 的最新進度併進自己的分支時，Git 不知道要留誰的，就把兩個版本都寫進檔案。
- 舞台
  - 初始畫面是一個檔案，沒有任何一行被標示：
    ```
    <<<<<<< HEAD
    送出申請
    =======
    確認送出申情
    >>>>>>> main
    ```
    說明列：「你在 feature/fix-typo 上執行 git merge main，Git 停下來了。」
  - 控制是三個選項（單選）：
    - 「你這邊的版本」：第 1～2 行亮起。說明列：「HEAD 就是『你現在站著的分支』。這是你的修改。」
    - 「併進來的版本」：第 4～5 行亮起。說明列：「這是 main 上同事的修改。」
    - 「解完之後」：畫面換成只有一行「確認送出申請」。說明列：「兩邊的修改都要保留，所以自己改成正確的一句，並刪掉標記那幾行。」
- （最後一張，無銜接句）

**重點回顧**（各對應一張卡的標題）
1. commit 是存檔；main 和分支都是標籤，標出某一顆 commit。
2. 新的存檔只推動你站著的那張標籤，所以在分支上改不會影響 main。
3. merge 把分岔的兩條線接起來；兩邊改到同一行時會衝突，要由人決定留什麼。

**隨堂檢測**
題目：你執行了 `git switch -c feature/fix-typo`，接著 commit 一次。這時 `main` 在哪裡？
- A. 移到你剛剛的新 commit
- B. 留在原本的位置（正確）
- C. 被刪掉了，merge 之後才會回來
選 A 的解釋：新的存檔只推動你站著的那張標籤，而你已經站到 feature/fix-typo 上了。
選 C 的解釋：開分支只是多貼一張標籤，原本的標籤不會消失。
選 B 的解釋：對。你站在 feature/fix-typo 上，所以只有它往前移。
（答錯可以重選；每個選項按下後顯示各自的解釋。）

**放在「動手做」分頁**：`git branch` 只貼標籤不會站過去（與 `git switch -c` 的差別）；快轉合併（fast-forward：你的分支沒有新存檔時，merge 不產生新 commit）；merge 與 rebase 的歷史圖對照；衝突標記在不同操作與設定下的差別（rebase 時兩側相反、diff3 樣式多一段）；解衝突後的 `git add` 與 `git commit`；tag 與版本；原有的手把手解答與練習任務。

### 第 2 課　我電腦裡的 Git，和 GitLab 上的是同一份嗎？（約 5 分鐘）
看完你能：說出 `git fetch`、`git pull`、`git remote update -p` 各自動到哪裡。

四張卡共用同一個場景：桌上的托盤，方塊代表 commit，標籤代表分支（與第 1 課的畫法一致）。每張卡只比前一張多一樣東西。各卡是獨立的畫面，初始狀態如各卡所寫，不受前一張卡的操作影響。

**卡 1　GitLab 上有一份，你電腦裡有一份，兩邊不會自動同步**
- 說明：公司 GitLab 上那一份稱為遠端。把你的存檔送上去叫 push。別人 push 之後，你的電腦不會自己知道。
- 舞台
  - 初始：兩個托盤「遠端（GitLab）」與「你的本機」，各有三個方塊 A、B、M。（本課為了畫面清楚，只畫 main 這條線上的三個方塊；M 是第 1 課把你的修正併進來的那個合併點，時間點是你的修正已經合併之後。）說明列：「兩邊現在一樣。」
  - 控制：一顆「同事 push 新的 commit」。按下：遠端托盤多一個方塊 E（同事的新修改），本機不變，按鈕停用。說明列：「遠端多了 E。你的電腦還不知道。」
- 銜接句：那你的電腦怎麼知道遠端長什麼樣子？

**卡 2　你的電腦裡還有一份「上次看到的遠端」**
- 說明：Git 在你電腦裡另外記了一份遠端的樣子，叫 `origin/main`（origin 是遠端的代稱）。`git status` 是跟這一份比，不會去問 GitLab。
- 舞台
  - 初始：三個托盤。遠端（A B M E）、快照 `origin/main`（A B M）、你的本機（A B M）。說明列：「中間這一份是你電腦裡記得的遠端。它還停在上次看到的樣子。」
  - 控制：一顆「git status」。按下：快照與本機兩個托盤被框起來（表示正在比較），遠端托盤變淡，按鈕停用。說明列：「它說 up to date（已是最新）。因為它只比中間和右邊，沒有看到左邊的 E。」
- 銜接句：要更新中間這一份，就是 fetch。

**卡 3　fetch 只更新快照，pull 還會更新你的本機**
- 說明：`git fetch` 把遠端的新東西複製到快照，不動你的本機。`git pull` 先做 fetch，再把快照的內容併進你站著的分支，檔案也跟著更新。
- 舞台
  - 初始：同卡 2 的三個托盤（遠端 A B M E；快照 A B M；本機 A B M）。說明列：「遠端有 E，另外兩邊還沒有。」
  - 控制是兩顆按鈕，可以任選其一按，按完兩顆都停用（要再試另一顆請按「重來」）：
    - 「git fetch」：一個 E 的複本從遠端移到快照（遠端的 E 留在原地）。說明列：「E 被複製到快照。你的本機沒有動，所以檔案還是舊的。」
    - 「git pull」：E 的複本先到快照，再到本機。說明列：「先更新快照，再更新你的本機。現在三邊一樣了。」
- 銜接句：還有一種情況：遠端的分支被刪掉了。

**卡 4　遠端刪掉的分支，快照裡的標籤還會留著**
- 說明：你的修正合併之後，GitLab 上的 `feature/fix-typo` 通常會被刪除。fetch 只會新增和更新，不會幫你刪；加上 `-p`（prune，修剪）才會清掉。
- 舞台
  - 初始：三個托盤的方塊都是 A B M。遠端與快照的 M 上各貼著一張 `feature/fix-typo` 標籤（快照那張寫 `origin/feature/fix-typo`）。說明列：「遠端和快照都還有這張分支標籤。」
  - 控制 1「GitLab 刪除 feature/fix-typo」：遠端那張標籤消失，方塊都還在。說明列：「遠端的標籤被撕掉了，存檔一個都沒少。快照那張還留著。」
  - 控制 2「git remote update -p」（控制 1 之後才可按）：快照那張標籤也消失。說明列：「-p 把快照裡已經過期的標籤清掉了。」
- （最後一張，無銜接句）

**重點回顧**（各對應卡片）
1. 有三份：遠端（GitLab）、你電腦裡的遠端快照（origin/main）、你的本機。
2. `git status` 只比快照和本機；fetch 更新快照；pull 再多更新你的本機。
3. 刪分支只是撕掉標籤；`git remote update -p` 會更新快照，並清掉遠端已刪除的標籤。

**隨堂檢測**
題目：你執行了 `git fetch`，打開檔案卻沒看到同事剛 push 的修改。為什麼？
- A. fetch 失敗了，要再執行一次
- B. fetch 只更新快照，你的本機要再 pull 才會跟上（正確）
- C. 同事的修改在遠端，fetch 抓不到
選 A 的解釋：fetch 有成功，新的存檔已經在快照裡了。
選 C 的解釋：fetch 抓的就是遠端的新東西。
選 B 的解釋：對。fetch 是「先抓回來放著，不動我的東西」。
（答錯可以重選。）

**放在「動手做」分頁**：三個指令的對照速查；`git status` 在三種狀態下的輸出；本機也有新存檔時 pull 會發生什麼（可能合併、可能要求先設定，依電腦設定而定）；`git remote update -p` 與 `git fetch --all --prune` 的關係；清掉自己本機的舊分支（先切回 main 並 pull，再 `git branch -d`；squash 合併時的例外）；編輯器可能會自動 fetch；實際在自己電腦重現的手把手步驟。

### 第 3 課　我的修改合併之後，是怎麼跑到使用者面前的？（約 5 分鐘）
看完你能：說出程式從 push 到上線會經過哪些關卡，以及出事時怎麼退回。

本課的流程圖固定七格，三張卡都用同一張圖：
① push　② 自動檢查　③ 審查並合併　④ 打包　⑤ Dev　⑥ UAT 驗收　⑦ Prod

**卡 1　push 之後，要過七道關卡才會到使用者面前**
- 說明：你把 C push 上去之後，不是「把檔案複製到伺服器」，而是走一條固定的流程，稱為 Pipeline。
- 舞台
  - 初始：七格都是「未執行」。說明列：「按『下一關』，一關一關往前走。」
  - 控制：一顆「下一關」。每按一次，下一格變為 ✓ 通過，說明列換成那一關的一句話；第七格之後按鈕停用。
    1. push：「你把 C 送到 GitLab。」
    2. 自動檢查：「機器把程式重新建置一次、跑測試、掃描安全問題。」
    3. 審查並合併：「同事看過你的修改，按下合併。機器確認能跑，人確認寫得對。」
    4. 打包：「把合併後的程式做成一包可以部署的東西，這一包就是 v1.4.0。」
    5. Dev：「自動部署到開發環境，開發者先看結果。」
    6. UAT 驗收：「部署到驗收環境，業務人員確認功能正確後簽核。」
    7. Prod：「在維護時段，由人按下按鈕，部署到正式環境。使用者看到修好的按鈕了。」
- 銜接句：如果其中一關沒過呢？

**卡 2　有一關沒過，後面的關卡就不會執行**
- 說明：這條流程的價值是把有問題的程式擋下來。（哪些關卡會擋、擋得多嚴，是每個專案自己設定的；這裡是常見的設定。）
- 舞台
  - 初始：七格都是「未執行」。說明列：「選一個情況，看流程停在哪裡。」
  - 控制是三個選項（單選）。選了之後，前面的格子 ✓ 通過，出事的那格 ✕ 失敗，後面的格子維持「未執行」：
    - 「測試沒過」：② 失敗。說明列：「停在自動檢查。打開紀錄看哪個測試失敗，修好再 push，流程會重跑。」
    - 「審查被退回」：③ 失敗。說明列：「停在審查。依同事的意見修改後再 push。」
    - 「驗收沒過」：⑥ 失敗。說明列：「停在 UAT。這一包不會上 Prod，使用者不受影響。」
- 銜接句：最後三格 Dev、UAT、Prod 都是「環境」，差在哪？

**卡 3　三個環境給三種人用，越後面換版越謹慎**
- 說明：同一包 v1.4.0 依序部署到三個環境。每個環境服務的對象不同，所以換版的條件也不同。
- 舞台
  - 初始：流程圖只強調最後三格，選取 Dev。
  - 控制是三個選項（單選）：Dev／UAT／Prod。畫面在被選的那一格下方顯示兩行：「誰在用」「誰決定換版」。
    - Dev：開發者／自動，main 一有新東西就換。說明列：「Dev 求快：越早看到整合後的結果越好。」
    - UAT：業務與測試人員／有人按下按鈕才換。說明列：「UAT 求穩：驗收到一半不能被換版。」
    - Prod：真正的使用者／驗收簽核後，在維護時段由人按下。說明列：「Prod 求不出錯：壞了客戶直接受影響。」
- 銜接句：萬一上了 Prod 才發現問題？

**卡 4　出事時先退回上一版，再慢慢查原因**
- 說明：退回上一版叫 Rollback。能不能退，取決於上線前有沒有把上一版那一包留著。
- 舞台
  - 初始：一個代表 Prod 的方塊，顯示「v1.4.0」與「✕ 使用者看到錯誤」。選項預設在「有留著 v1.3.0」。說明列：「正式環境出事了。」
  - 控制：兩個選項（單選）「有留著 v1.3.0／沒留 v1.3.0」，加一顆「Rollback」。切換選項會把方塊重設回初始的錯誤狀態。
    - 有留，按 Rollback：方塊變成「v1.3.0」與「✓ 恢復正常」。說明列：「幾分鐘內恢復。原因可以之後慢慢查。」
    - 沒留，按 Rollback：方塊維持「v1.4.0」與「✕ 使用者看到錯誤」。說明列：「沒有現成的那一包，只能從舊的原始碼重新打包，這段時間使用者持續看到錯誤。」
- （最後一張，無銜接句）

**重點回顧**（各對應卡片）
1. 程式上線要依序通過七道關卡；有一關沒過，後面就不會執行。
2. Dev、UAT、Prod 給不同的人用，越後面換版越謹慎。
3. 出事先 Rollback 再查原因，前提是上一版那一包有留著。

**隨堂檢測**
題目：「自動檢查」裡的測試沒過，接下來會怎樣？
- A. 流程繼續，先部署到 Dev 再請人看
- B. 流程停在這一關，不會打包，也不會部署到任何環境（正確）
- C. 系統自動 Rollback 到上一版
選 A 的解釋：沒過的關卡後面都不會執行，包含部署到 Dev。
選 C 的解釋：Rollback 是已經部署出去之後的事，這裡還沒部署。
選 B 的解釋：對。有問題的程式被擋在最前面。
（答錯可以重選。）

**放在「動手做」分頁**：Rollback 不只要留上一版那一包，還要準備資料庫的回復指令、跟著版本走的設定、部署紀錄（四樣東西的速查）；哪些步驟該自動化的分類練習；哪些設定會改變「沒過就停」（允許失敗的工作、合併前是否強制要求檢查通過）；Dev 實際上每次合併都會部署一次，v1.4.0 是被選來發行的那一包；原有的手把手解答與練習任務。

## 第三部分：事實性陳述（供查核）

1. `git status` 顯示的 up to date／behind 是與本機的遠端追蹤分支（origin/main）比較，不會連線到遠端。
2. `git fetch` 預設不會刪除遠端已不存在的遠端追蹤分支；需加 `--prune`，或設定 `fetch.prune=true`。
3. `git pull` 會先 fetch，再把上游分支整合進目前所在的分支。目前分支沒有自己的新 commit 時是快轉。兩邊分岔時，行為依 `pull.rebase`／`pull.ff` 設定而定；完全沒有設定時 Git 會拒絕並要求指定。Git for Windows 的系統設定預設 `pull.rebase=false`（合併）。
4. `git remote update -p` 會對所有遠端執行更新並修剪，效果等同 `git fetch --all --prune`。
5. 修剪只移除遠端追蹤分支（標籤），不會刪除任何 commit，也不會刪除本機分支。
6. `git branch <名稱>` 只建立分支、不切換；`git switch -c <名稱>`（或 `git checkout -b`）建立並切換。新的 commit 只會移動目前所在分支（HEAD 指向的分支）的指標。
7. 兩條分岔的歷史 merge 會產生一個有兩個上一步的合併 commit。可快轉時，`git merge` 預設不產生合併 commit；GitLab Merge Request 預設的合併方式則一律產生合併 commit。
8. 在 `git merge` 的衝突標記中，`<<<<<<< HEAD` 到 `=======` 之間是目前所在分支的內容，`=======` 到 `>>>>>>> 名稱` 之間是被併入那一方的內容。rebase 時兩側的意義相反；`merge.conflictStyle=diff3` 時會多一段共同祖先的內容。
9. GitLab CI 中，同一條 Pipeline 內前一個階段的工作失敗時，後續階段預設不會執行；`allow_failure`、`needs`、`when` 可以改變這個行為。審查與合併、UAT 驗收不是 Pipeline 的階段：測試失敗能否擋下合併，取決於專案是否啟用「Pipeline 必須成功」的合併檢查；驗收是人的判斷。
