# spec-v2 的最終修訂（第 3 輪表態後）

本檔與 spec-v2.md 一起構成定稿。兩者不一致時，**以本檔為準**。

## 第一部分的修訂

1. **「你在這裡」記號**：永遠貼在某一張分支標籤旁邊（不是貼在方塊上）。第 1 課卡 1 的初始狀態改為：`main` 標籤在 A，「你在這裡」在 `main` 旁。
2. **顏色**：刪除「剛剛發生變化的物件用蜂蜜黃」。改為：通過的格子一律綠色加 ✓；「目前這一步」的物件另外加 2px 深色框。蜂蜜黃只用在選取中的選項、主要按鈕、進度列目前位置。
3. **3D 場景指的是第 2 課的托盤場景**（四張卡共用同一種畫法）。其餘舞台都是一般的平面元件。
4. **重點回顧**：三點合起來涵蓋該課所有卡片，不要求一點對一張卡。
5. **歷史表新增一列**：E＝同事在你的修正合併之後，又 push 的一個新修改（在 main 上，只在第 2 課出現）。

## 第 1 課的修訂

- 卡 3：本卡不顯示「你在這裡」記號。控制 2 的說明列改為：「M 同時接上 D 和 C。在公司裡，這一步通常是在 GitLab（公司放程式碼的網站）上按下合併按鈕完成的。」
- 卡 4 說明改為：「這叫衝突。**假設**同事的 D 也把那顆按鈕改成『確認送出申情』。合併之前，你先把 main 的最新進度併進自己的分支（方向和上一張卡相反），Git 不知道要留誰的，就把兩個版本都寫進檔案。」
- 卡 4「解完之後」的說明列改為：「兩邊的修改都保留，改成正確的一句。標記那幾行要刪掉。」

## 第 2 課的修訂

- **托盤裡的方塊**：所有托盤都畫五個方塊 A、B、C、D、M（不是只畫 A、B、M）。時間點是你的修正已經合併之後。卡 1、2、3 新增的方塊是 E。
- 開頭那句「每張卡只比前一張多一樣東西」改為：「卡 2 多一個托盤，卡 3 多兩個指令，卡 4 多分支標籤。」
- 卡 1 初始：兩個托盤各有 A B C D M。按下後遠端多 E。
- 卡 2、卡 3 初始：遠端 A B C D M E；快照與本機 A B C D M。
- 卡 4：
  - 說明改為：「你的修正合併之後，GitLab 上的 `feature/fix-typo` 通常會被刪除。一般的 fetch 只會新增和更新，不會幫你刪。`git remote update -p` 會更新快照，並清掉遠端已經刪除的分支標籤（-p 是 prune，修剪的意思）。」
  - 初始：三個托盤的方塊都是 A B C D M。遠端的 **C** 上貼著 `feature/fix-typo`，快照的 **C** 上貼著 `origin/feature/fix-typo`。（合併之後分支標籤留在 C，不會移到 M。）
  - 兩個控制的結果不變：先撕掉遠端那張，再撕掉快照那張；方塊都不會少。
- 「動手做」分頁另外要寫到：
  - 設定 `fetch.prune=true` 之後，一般的 fetch 與 pull 也會修剪。
  - `git remote update -p` 在沒有設定 `remotes.default` 時，效果等同 `git fetch --all --prune`。
  - 實際在自己的分支上跟上最新進度時，通常是 `git fetch` 後 `git merge origin/main`，這時衝突標記的結尾會是 `>>>>>>> origin/main`。

## 第 3 課的修訂

- 課名改為：「我的修改，是怎麼從我的電腦跑到使用者面前的？」
- 「看完你能」下面加一句時間說明：「這一課回到你剛 commit 完 C、還沒合併的時候，把整條路從頭走一次。」
- 七格的說法：整條路有七道關卡，其中由機器自動執行的部分稱為 Pipeline。不要把七格全部稱為 Pipeline。
- 卡 1 說明改為：「你把 C push 上去之後，不是『把檔案複製到伺服器』，而是要依序通過七道關卡。其中機器自動做的部分，稱為 Pipeline。」
- 卡 1 各關的說明列文字修訂：
  - 2 自動檢查：「機器把原始碼重新組成可以執行的程式（建置）、跑測試、掃描安全問題。」
  - 4 打包：「機器把合併後的程式做成一包可以部署的東西，這一包就是 v1.4.0。」
  - 6 UAT 驗收：「部署到 UAT（給業務驗收用的環境），業務人員確認功能正確後簽核。」
- 隨堂檢測題幹改為：「在這一課的流程裡（檢查沒過就不能合併），『自動檢查』的測試沒過，接下來會怎樣？」

## 第三部分的修訂

- 第 4 條改為：「`git remote update -p` 會對遠端執行更新並修剪。未設定 `remotes.default` 時，效果等同 `git fetch --all --prune`。」

## 尚未驗證、需要使用者確認的事
- GitLab 新專案是否預設啟用「Pipeline 必須成功才能合併」。審查者認為預設未啟用，但沒有 GitLab 可以實測。第 3 課已改為明寫前提，不受影響；公司實際設定請使用者確認。
