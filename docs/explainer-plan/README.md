# 互動講解：全教材規劃與接手說明

這個資料夾是「把全站教材改成互動講解」的規劃。讀完這一份就能接手繼續做，不需要之前的對話紀錄。

## 現況（2026-11-17）

- 平台有 3 條路線、34 門課、88 章，全部都有文字教材。
- 新的頁面架構已上線：課程頁只列出各課；每課一頁，上方分「講解」「動手做」。沒有互動講解的章節只顯示動手做的內容。
- **已完成互動講解的只有 `devops-basics` 一門課（3 章）**，使用者已看過並接受這種呈現方式。
- 其餘 85 章的規劃在本資料夾的四份文件裡。規劃只到「每張卡的結論與舞台要呈現什麼」，還沒寫到逐字腳本，也還沒實作。

## 使用者的要求（不要違反）

1. **先討論，再動手**。方向有疑問先問，不要直接做大改動。
2. 使用者不懂大部分的教材內容，所以**不能請他審內容的正確性**；正確性要靠實測與多模型審查把關。他能判斷的是「看不看得懂」「看起來舒不舒服」。
3. 使用者退回過一版，原因是：像把知識一口氣灌進去、沒有引導、看不出重點、一張卡塞太多、顏色與框線全部在搶注意力。新做法就是為了避免這些。
4. 進度追蹤功能（學習狀態下拉、完成度）使用者說可以拿掉，但還沒做；筆記、作品集、面試題的「我的回答」要保留。
5. 回報要誠實：功能做了但內容沒填、驗證沒做到的，要明講。

## 做法（每一門課照這個流程）

方法寫成了 skill：`interactive-lesson`（在使用者的 `claude-skills` repo，裝到使用者層後可用）。
核心是五條原則：一課一頁只回答一個問題；一張卡一句結論；一個舞台只有三層；只有一個強調色；整門課共用一個例子。

1. **讀規劃**：打開該路線的規劃文件，找到這門課的 A（教材問題）與 B（互動講解規劃）。
2. **先修教材問題**：A 項列的「會教錯」先修（改 `src/data/courses.json`、`lessonTeachings.json`），每一條都要實測或查證後才改。
3. **寫逐字腳本**：把 B 項的規劃擴寫成腳本，細度比照 `reference/devops-basics-spec.md`：每個舞台的初始狀態、每個控制按下後的畫面與說明列的確切文字、重點回顧、檢測題與每個選項的解釋、移到動手做的清單、事實性陳述。
4. **查核腳本**：事實性陳述逐條實測。有 `adversarial-review` skill 就用白箱模式審（新人讀者、教學設計、技術正確性、規格自洽四個面向），裁決後修腳本，再把修正版查一次。沒有的話，至少開新的 subagent 扮演新人讀者，另一個負責實測。
5. **實作**：
   - 腳本搬進 `src/data/lessonExplainers.json`（資料格式見 `src/types.ts` 的「互動講解」段落與 `.claude/skills/course-builder/references/data-model.md`）。
   - 現有場景能用就用（`src/components/lesson/` 的 graph／file／trays／gates／prod）。需要新場景時照 `roadmap.md` 的清單做，一種場景要能被多章共用。
   - 動手做的補充內容放 `lessonTeachings.json` 的 `extras`。
   - 新名詞補進 `src/data/glossary.json`。
6. **驗證**：
   - `node .claude/skills/course-builder/scripts/validate.mjs` 與 `npm run build` 都要通過。
   - 用無頭瀏覽器實際操作每張卡並截圖（`interactive-lesson` skill 的 `tools/cdp.mjs`），桌機寬 1360 與手機寬 390 都拍，照 skill 的 `references/acceptance-checklist.md` 逐條檢查。
7. **回報並請使用者看**，一門課一門課交，不要一次做完一整條路線才給他看。
